# RAGAS Evaluation

This directory contains scripts and utilities for evaluating the StudyGraph RAG pipeline using the **RAGAS** library.

## Prerequisites

- Python 3.10+ (type‑union syntax `float | None` is used).
- `OPENAI_API_KEY` set in your environment.
- All project dependencies installed, including the newly added `ragas[all]` and `tqdm`:

```bash
pip install -r backend/requirements.txt
```

## Running the evaluation

The entry point is the module `backend.eval.ragas_evaluation`. Execute it with:

```bash
python -m backend.eval.ragas_evaluation
```

The script will:
1. Load environment variables (`.env`).
2. Initialise the LLM client and Chroma vector store.
3. Download the RAGEval benchmark dataset from HuggingFace.
4. For each sample, call the StudyGraph RAG pipeline (`engine.rag_query`).
5. Collect the generated answer and the retrieved context chunks.
6. Compute the four standard RAGAS metrics:
   - **answer_relevancy**
   - **faithfulness**
   - **answer_similarity**
   - **context_recall**
7. Write a JSON report to `backend/eval/reports/` named `ragas_report_<timestamp>.json`.

## Interpreting the report

The JSON file contains a list of dictionaries, one per sample, with the following keys:
- `question` – the original user query.
- `answer` – the answer generated by your RAG pipeline.
- `ground_truth` – the reference answer from the RAGEval dataset.
- `contexts` – the text chunks retrieved for this query.
- Metric scores (`answer_relevancy`, `faithfulness`, `answer_similarity`, `context_recall`).
- An optional `overall_score` that can be added by averaging the metrics.

Higher scores indicate better performance. You can aggregate the scores (e.g., mean) to get an overall view of your system.

## Custom test data

If you prefer to evaluate on your own documents, place a JSONL file in `backend/eval/data/` where each line follows the same schema as the RAGEval samples (`question`, `ground_truth`, `contexts`). Adjust the script to load that file instead of `RAGEvalDataset.download_rageval_dataset()`.

## Extending the evaluation

- **Additional metrics**: Import any other RAGAS metrics and include them in the `metrics` list.
- **CI integration**: Add a Makefile target:

```makefile
ragas-eval:
	python -m backend.eval.ragas_evaluation
```

You can then fail the CI job if the average of selected metrics falls below a threshold.

# Concept extraction evaluation

`concept_eval.py` checks how well StudyGraph pulls concepts out of a document. It compares the concepts StudyGraph extracted with a list a person built by reading the original PDF, and reports precision, recall and F1. It needs no API keys and no ML packages.

## 1. Build the reference list

For each document you want to score:

1. Read the original PDF, not StudyGraph's output, so the list is not biased by what the system found.
2. Write down every concept a student would need to learn from it. Agree a rule before you start, for example "named ideas, methods and terms that are defined or explained, not every noun".
3. If two people annotate, compare lists and settle disagreements. Record who annotated in the file.
4. Add synonyms for names that have a common short form, such as `1NF` for first normal form.

Save it as JSON. One document:

```json
{
  "document": "week3-normalisation.pdf",
  "annotator": "Lee, checked by Aadhir",
  "concepts": [
    "Normalisation",
    {"name": "First normal form", "synonyms": ["1NF"]}
  ],
  "relationships": [
    {"from": "Normalisation", "to": "First normal form"}
  ]
}
```

Several documents go in `{"documents": [ ... ]}`. `document` must be the file name as uploaded to StudyGraph. `relationships` is optional.

Keep real reference files in `eval/data/` (ignored by git) or commit them on purpose if the team agrees. The files in `eval/examples/` are made up and only show the format.

## 2. Run it

From the `backend` folder.

Against a JSON export of extracted concepts:

```bash
python -m eval.concept_eval --reference eval/data/week3.json --extracted eval/data/week3_extracted.json
```

The extracted file can be a plain list of names, `{"concepts": [...]}`, `{"documents": [...]}` in the same shape as the reference, or a saved graph version with `concepts`, `relationships` and `concept_provenance`.

Straight from Supabase, using a signed-in user's token so row level security applies:

```bash
export STUDYGRAPH_ACCESS_TOKEN=...   # see below
python -m eval.concept_eval --reference eval/data/week3.json --graph-id <graph uuid> [--version-id <version uuid>]
```

Without `--version-id` the latest sealed version is used. Concepts are filtered to the reference `document` through `concept_provenance`, so one graph with many uploads can be scored file by file.

To get the token, open StudyGraph in the browser, open DevTools, then Application, Session Storage, and the key starting with `studygraph.auth.`. Copy `access_token`. It expires after about an hour. The graph id appears in network requests such as `/api/graphs/<graph id>/versions`. Never commit the token.

Options:

| Option | Meaning |
|---|---|
| `--fuzzy 0.9` | Also match names at least this similar (character ratio). Off by default. Report it if you use it. |
| `--out DIR` | Where reports go. Default `eval/reports/` (ignored by git). |
| `--no-files` | Print the table only. |

## 3. What the numbers mean

* TP: an extracted concept matched a reference concept.
* FP: an extracted concept that is not in the reference.
* FN: a reference concept StudyGraph did not extract.
* Precision = TP / (TP + FP). Recall = TP / (TP + FN). F1 = 2PR / (P + R).
* If a denominator is zero the score is shown as `n/a`, never as 0 or 1.
* Micro average adds up TP, FP and FN over all documents. Macro average is the mean of the per document scores.

Matching is one to one and runs in this order, each step only on what is still unmatched:

1. exact match after normalisation (same rules as `graph_fusion.normalize_concept`: lower case, hyphens to spaces, some punctuation removed, spaces collapsed)
2. plural of the last word (`primary keys` and `primary key`)
3. a synonym listed in the reference
4. fuzzy, only with `--fuzzy`

Names that normalise to the same text are counted once and listed under `duplicates_ignored`. Relationships are scored separately as unordered concept pairs, after renaming extracted concepts to the reference concept they matched. The relation type is not compared.

Each run writes `concept_eval_<time>.json` (every match, miss and extra), `.csv` (one row per document) and `.md` (the table plus the lists). Look at the false positive list before trusting a low precision: some will be real concepts the annotators missed, and the reference should be fixed, not the score.

Tests: `python -m pytest tests/test_concept_eval.py`.

## Why JSON files are not uploads

The upload area accepts PDF, DOCX, PPTX, TXT and MD learning material. A JSON file is not learning material, so the workspace rejects it with a message pointing here. Reference concept lists are evaluation data and are used only by this tool.
